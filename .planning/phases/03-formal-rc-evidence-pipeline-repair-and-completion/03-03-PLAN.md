# Phase 3 Plan 3: Artifact Gates And Formal Evidence Handoff

<objective>
Build formal artifacts from the selected formal run only through the artifact
builder, respect readiness and claim-guard gates, and write a Phase 3 handoff
that tells Phase 4 exactly which formal source run and gate status to diagnose.
</objective>

<scope>
## In Scope

- Build diagnostic or claim-ready artifacts from the selected formal run using
  `scripts/build_artifacts.py`.
- Validate formal readiness JSON compatibility before any `--claim-ready`
  artifact build.
- Build manuscript-frame metadata only within claim-guard boundaries.
- Write `.planning/results/PHASE3_FORMAL_EVIDENCE_HANDOFF.md` with selected
  run path, readiness status, artifact status, claim guard status, and next
  Phase 4 inputs.

## Out Of Scope

- Editing artifact tables, figures, rows, or claim guard JSON by hand.
- Upgrading abstract, introduction, contribution, conclusion, or manuscript
  claims.
- Performing Phase 4 effect-size, paired-difference, confidence-interval, or
  claim-ladder diagnosis.
</scope>

<tasks>
## Task 1: Choose Artifact Mode From Readiness Gates

**Type:** audit
**Files:** `work2_coding/outputs/phase5_readiness/formal_robust_menu/FORMAL_READINESS.json`,
`work2_coding/outputs/formal_v1/formal_robust_menu/*/study_summary.json`,
`work2_coding/Src/artifact_status.py`

**Action:**

1. Select the formal source run validated by Plan 2.
2. Read `FORMAL_READINESS.json`.
3. If readiness `status` is `passed`, `claim_ready_allowed` is true,
   `git_dirty` is false, the dependency snapshot exists, and manifest/checkpoint
   hashes match the selected run, allow a claim-ready artifact build.
4. Otherwise choose diagnostic artifact mode with `--allow-incomplete` and
   record the reason.

**Verify:**

- Claim-ready build mode is never selected while readiness is blocked.
- Diagnostic mode is explicit and does not downgrade the value of completed
  rows; it only blocks manuscript superiority claims.

**Acceptance Criteria:**

- The artifact build command is determined by gates, not by desired paper
  wording.

## Task 2: Build Formal Artifact Bundle Through Builder Only

**Type:** artifacts
**Files:** `work2_coding/scripts/build_artifacts.py`,
`work2_coding/Src/artifact_builder.py`,
`work2_coding/outputs/phase3_formal_artifacts/`

**Action:**

For diagnostic mode, run from `work2_coding/`:

```powershell
python scripts/build_artifacts.py --run-dir <selected-formal-run-dir> --output-root outputs/phase3_formal_artifacts --allow-incomplete --readiness-json outputs/phase5_readiness/formal_robust_menu/FORMAL_READINESS.json
```

For claim-ready mode, run:

```powershell
python scripts/build_artifacts.py --run-dir <selected-formal-run-dir> --output-root outputs/phase3_formal_artifacts --claim-ready --readiness-json outputs/phase5_readiness/formal_robust_menu/FORMAL_READINESS.json
```

Then read `outputs/phase3_formal_artifacts/ARTIFACT_STATUS.json` and confirm:

- `source_run_dir` points at the selected formal run
- `row_count` matches the selected run
- `formal_claim_ready` is true only in claim-ready mode
- checkpoint and readiness metadata are present when required
- placeholder-only artifacts are not presented as formal evidence

**Verify:**

- `RC-05` artifact generation is builder-derived.
- Artifact status explains diagnostic, incomplete, blocked, or claim-ready
  state.

**Acceptance Criteria:**

- Formal tables, figures, summaries, and status files exist only as generated
  artifacts with source metadata.

## Task 3: Build Manuscript Frame Within Claim Guard

**Type:** artifacts
**Files:** `work2_coding/scripts/build_manuscript_frame.py`,
`work2_coding/Src/manuscript_claims.py`,
`work2_coding/outputs/phase3_formal_artifacts/manuscript/CLAIM_GUARD.json`

**Action:**

Run from `work2_coding/`:

```powershell
python scripts/build_manuscript_frame.py --artifact-root outputs/phase3_formal_artifacts
```

Read `CLAIM_GUARD.json` and confirm:

- empirical superiority is blocked unless `claim_ready` and
  `formal_claim_ready` are true
- no-filter remains diagnostic
- attention remains V2/diagnostic
- diagnostic/status tables are allowed when artifact status exists

**Verify:**

- Manuscript frame output does not upgrade positive empirical claims while
  gates are blocked.
- Claim guard status is machine-readable for Phase 4 and later manuscript work.

**Acceptance Criteria:**

- The manuscript-facing boundary is generated from artifact status, not edited
  by hand.

## Task 4: Run Artifact Gate Tests And Write Handoff

**Type:** verify
**Files:** `work2_coding/scripts/test_artifact_gates.py`,
`.planning/results/PHASE3_FORMAL_EVIDENCE_HANDOFF.md`,
`work2_coding/outputs/phase3_formal_artifacts/ARTIFACT_STATUS.json`,
`work2_coding/outputs/phase3_formal_artifacts/manuscript/CLAIM_GUARD.json`

**Action:**

1. Run from `work2_coding/`:

   ```powershell
   python scripts/test_artifact_gates.py
   ```

2. Write `.planning/results/PHASE3_FORMAL_EVIDENCE_HANDOFF.md` with:
   - selected formal run directory and run ID
   - readiness JSON path, status, blocker list, checkpoint hash/load status
   - artifact root, artifact status, and claim-ready flags
   - claim guard allowed/blocked claims summary
   - whether Phase 4 should diagnose strong, conditional, weak/diagnostic, or
     unsupported claims from formal rows
   - any remaining blockers or user decisions needed before claim-ready
     manuscript language.

**Verify:**

- Artifact gate tests pass or blockers are documented.
- Handoff points Phase 4 to generated rows and status artifacts.
- Handoff does not classify final claim strength; it only names inputs and gate
  status.

**Acceptance Criteria:**

- Phase 4 can begin result diagnosis without re-discovering run provenance or
  artifact gate state.
</tasks>
