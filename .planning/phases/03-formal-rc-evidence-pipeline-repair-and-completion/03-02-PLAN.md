# Phase 3 Plan 2: Formal Replay Row Validation And Completion

<objective>
Validate the latest completed formal RC run as comparable seven-tag formal
evidence, or rerun `formal_robust_menu` after preflight blockers are resolved.
If replay fails, preserve failed rows and write a failure diagnosis instead of
editing generated outputs.
</objective>

<scope>
## In Scope

- Validate the latest completed formal run directory and row schema.
- Check row count, split coverage, policy coverage, execution status,
  checkpoint status, paired fields, opt-out accounting, and error metadata.
- Rerun formal replay only when candidate rows fail validation or readiness
  requires a fresh formal source run.
- Write `.planning/results/FORMAL_FAILURE_DIAGNOSIS.md` when replay fails or
  candidate rows are not comparable.

## Out Of Scope

- Tuning formal manifest parameters based on formal results.
- Deleting or hiding failed run directories.
- Manually editing `normalized_rows.json`, CSV rows, study summaries, blockers,
  or paper artifacts.
- Diagnosing claim strength; that belongs to Phase 4.
</scope>

<tasks>
## Task 1: Validate Candidate Completed Formal Run

**Type:** verify
**Files:** `work2_coding/outputs/formal_v1/formal_robust_menu/formal_robust_menu-20260614T032323Z-c672286a/study_summary.json`,
`work2_coding/outputs/formal_v1/formal_robust_menu/formal_robust_menu-20260614T032323Z-c672286a/normalized_rows.json`,
`work2_coding/Experiments/studies/formal_robust_menu.yaml`

**Action:**

1. Read `study_summary.json` and confirm:
   - `execution_status: completed`
   - `row_count: 35`
   - `checkpoint_statuses: [loaded]`
   - all seven mainline policy tags
   - five formal split IDs
   - uptake regimes include `low` and `medium`
2. Read `normalized_rows.json` and confirm rows cover exactly
   `5 splits x 7 policies`.
3. Confirm each row has `status: completed`, `execution_status: completed`,
   `placeholder_only: false`, `checkpoint_load_status: loaded`, and no
   non-empty `error_type` or `error_message`.
4. Compare the run's manifest hash and manifest snapshot against the current
   manifest. If the current manifest changed, record whether the candidate run
   remains valid for diagnostics or must be rerun.

**Verify:**

- `RC-04` candidate evidence is either accepted as complete/comparable or
  rejected with a concrete reason.
- The existing `git_dirty: true` is recorded as a claim-readiness blocker, not
  as row incomparability by itself.

**Acceptance Criteria:**

- The executor can point to one formal source run for Phase 4 diagnosis or a
  documented reason to rerun.

## Task 3: Rerun Formal Replay Only If Needed

**Type:** experiment
**Files:** `work2_coding/scripts/run_study.py`,
`work2_coding/Src/study_execution.py`,
`work2_coding/outputs/formal_v1/formal_robust_menu/`

**Action:**

If Task 1 rejects the candidate run, or if readiness/gate policy requires a new
formal source run after provenance cleanup, run:

```powershell

python scripts/run_study.py --study formal_robust_menu --execute --output-root outputs/formal_v1
```

After the run:

1. Read the printed run directory and `study_summary.json`.
2. If `execution_status` is `completed`, repeat Task 1 validation on the new
   run.

   write `.planning/results/FORMAL_FAILURE_DIAGNOSIS.md`.
4. Do not tune manifest settings based on observed formal ranking.

**Verify:**

- Completed formal replay writes comparable normalized rows.
- Failed replay writes failed or blocked rows with structured error metadata.
- The output root remains under `work2_coding/outputs/formal_v1/`.

**Acceptance Criteria:**

- Phase 3 has either completed comparable formal rows or an explicit failed-run
  diagnosis ready for Phase 4/Phase 5 routing.
