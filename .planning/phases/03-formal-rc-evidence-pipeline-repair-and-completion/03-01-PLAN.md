# Phase 3 Plan 1: Formal Readiness And Blocker Diagnosis

<objective>
Inspect the formal RC manifest and readiness surface, verify the required
shared checkpoint or identify the exact blocker, and write a non-destructive
dirty-git/readiness diagnosis before any formal replay or artifact claim gate
is advanced.
</objective>

<scope>
## In Scope

- Inspect `formal_robust_menu.yaml`, related robust-menu manifests, and the
  readiness command output.
- Verify the formal checkpoint path, hash, load status, and provenance fields.
- Run lightweight script-style contract tests for readiness and checkpoint
  provenance.
- Write `.planning/results/FORMAL_BLOCKER_DIAGNOSIS.md` when dirty git or
  checkpoint readiness blocks claim-ready use.

## Out Of Scope

- Reverting, staging, deleting, stashing, or cleaning user changes.
- Hand-editing generated result rows, artifact tables, artifact figures, or
  manuscript claim language.
- Claiming empirical superiority from the candidate formal run.
- Creating or using an `ooh_code/` runtime root.
</scope>

## Task 2: Verify Or Diagnose Shared Checkpoint Readiness

**Type:** verify
**Files:** `work2_coding/outputs/shared_training/work2_robust_menu/formal/supervised_ml.pt`,
`work2_coding/outputs/phase5_readiness/formal_robust_menu/FORMAL_READINESS.json`,
`work2_coding/Src/formal_readiness.py`,
`work2_coding/Src/Algorithms/Agent.py`,
`work2_coding/scripts/test_checkpoint_provenance.py`

**Action:**

1. Check whether the required checkpoint file exists.
2. Read or regenerate readiness with:

   ```powershell
   cd work2_coding
   python scripts/check_formal_readiness.py --study formal_robust_menu --output-root outputs/phase5_readiness
   ```

   If a diagnostic-only rerun is needed while dirty git is known, use the
   existing script's documented diagnostic behavior and keep the output marked
   blocked/diagnostic.
3. Record checkpoint resolved path, SHA-256 hash, load status, model type, and
   sidecar/dependency snapshot availability.
4. If checkpoint is missing or load status is not `loaded`, run:

   ```powershell
   python scripts/train_shared_checkpoint.py --study formal_robust_menu --checkpoint-path outputs/shared_training/work2_robust_menu/formal/supervised_ml.pt
   ```

   Then rerun readiness. Do not retrain merely to change results when the
   existing checkpoint is already loaded and provenance is usable.

**Verify:**

- `RC-02` is covered: checkpoint exists or the blocker and regeneration command
  are documented.
- `checkpoint_load_status` is explicitly `loaded` before formal replay is
  considered comparable.
- `python scripts/test_checkpoint_provenance.py` passes.

**Acceptance Criteria:**

- The formal checkpoint state is reproducible from metadata, not inferred from
  file existence alone.

## Task 3: Diagnose Dirty Git And Formal Readiness Blockers

**Type:** docs
**Files:** `.planning/results/FORMAL_BLOCKER_DIAGNOSIS.md`,
`work2_coding/outputs/phase5_readiness/formal_robust_menu/FORMAL_READINESS.json`

**Action:**

1. Run `git status --short` from the repository root.
2. Categorize dirty paths into planning, runtime, manuscript/paper, generated
   artifacts, and unrelated notes.
3. Read `FORMAL_READINESS.json` blockers and map each blocker to an action:
   keep diagnostic, ask user to commit, ask user to stash, or rerun readiness
   after user-confirmed cleanup.
4. Write `.planning/results/FORMAL_BLOCKER_DIAGNOSIS.md` with:
   - readiness command and status
   - dirty-git blocker details
   - checkpoint load status and hash
   - changed path categories
   - explicit non-destructive recommendations
   - a note that claim-ready formal artifacts cannot be promoted until
     readiness passes without bypassing blockers.

**Verify:**

- `RC-03` is covered by a readiness result or blocker diagnosis.
- The diagnosis requests user confirmation before destructive cleanup or broad
  git-state mutation.
- The document does not recommend `git reset --hard` or automatic revert.

**Acceptance Criteria:**

- Claim-ready readiness status is clear enough that Phase 3 can continue
  diagnostically or pause for user cleanup without damaging unrelated work.
